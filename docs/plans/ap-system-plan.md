# AP 行动经济系统专项计划（ap-system-plan）

> 状态：**待讨论（S4 完成后、S5 实施前）**
> 创建日期：2026-09-19
> 上级路线图：`docs/plans/gameplay-system-roadmap.md`
> 所属基础模块：S1 / M1.2 游戏时钟、回合与行动经济
> 适用范围：S3 / S4 / S5 / S6 / S8

---

## 一、为什么要单独讨论

AP 当前已经影响：

- 与参谋对话。
- 下达命令。
- 情报工作项处理。
- 航线提案与修订。
- 标图审批。
- 推进时间。
- 后续判断、通信和行动。

但 AP 目前没有一个独立、完整的规格。这会导致：

- 同一个动作在不同系统里重复扣费或不扣费。
- 玩家为了避免浪费 AP，不敢阅读或询问。
- AP 只限制操作，却不创造新的决策。
- AP 与游戏时间、通信延迟和参谋工作量互相重复。
- NPC 自动工作与玩家动作的边界不清。

因此，AP 必须先回答“它为什么存在”，再决定具体费用。

---

## 二、本计划要回答的问题

## 2.1 AP 的目的

- 控制决策稀缺性。
- 制造时间与行动取舍。
- 表示 commander 的注意力预算。
- 控制 LLM 交互成本。
- 只是历史模拟中的抽象？

必须明确 AP 主要解决哪个问题。

## 2.2 AP 的基本单位

需要逐一决定：

```text
阅读电文
普通交谈
要求正式判断
回答澄清
批准提案
驳回提案
要求修订
签发命令
取消命令
修改命令
推进时间
```

哪些消耗 AP，哪些免费。

## 2.3 AP 与时间

- AP 是否只是每 tick 的行动预算。
- 等待是否回复 AP。
- 命令延迟期间能否继续行动。
- 推进时间是否等于结束回合。
- AP 用完是否必须推进时间。
- 是否可以保留未用 AP。

## 2.4 AP 的生成与重置

- 固定每回合重置。
- 普通 / 关键 / 紧急回合。
- 根据 commander 状态或参谋负载变化。
- 是否允许通过冒险决策获得临时 AP。
- AP 不足时是否存在超支或代价机制。

## 2.5 AP 与角色工作量

需要区分：

```text
玩家注意力 AP
参谋工作负载
通信延迟
命令执行延迟
```

避免四层机制重复惩罚同一行为。

## 2.6 重试与纠错

- 同一问题重复提问是否收费。
- 参谋回答错误后要求修正是否收费。
- commander 修改自己的命令是否收费。
- 通信失败后的重发是否收费。
- 审批流程中的往返是否收费。

## 2.7 防刷与防卡

- 不能通过反复询问刷新判断。
- 不能因 AP 不足而无法处理紧急威胁。
- 不能强迫玩家为了阅读文档消耗 AP。
- 不能出现“无操作但必须推进时间”的死循环。

## 2.8 UI

- 顶栏 AP 显示。
- 每个操作按钮显示成本。
- 成本不足时显示原因。
- 哪些操作免费必须明确。
- AP 变化写入 LOG 和战后复盘。

## 三、候选模型

至少在讨论中比较：

### A. 无 AP，纯时间驱动

玩家随时操作，所有压力来自真实时间延迟和敌方行动。

### B. 传统行动点

每个回合固定 AP，所有正式动作按点消耗。

### C. Commander Attention Budget

只限制 commander 能处理的复杂事项，阅读和查看免费。

### D. Command Bandwidth

命令和通信消耗“带宽”，普通对话不消耗。

### E. Staff Workload

不限制玩家，而限制参谋能并行处理多少事项。

### F. 混合模型

例如：阅读免费、询问消耗注意力、命令受通信与执行时间限制。

最终选择需要试玩验证，不应先入为主保留现有 AP。

---

## 四、与其他系统的边界

| 系统 | AP 专题需要确定 |
|---|---|
| S3 认知 | 询问、重判、查看判断是否消耗 AP |
| S4 沟通 | 核心参谋沟通、提醒回复是否消耗 AP |
| S5 命令 | 签发、修改、取消 Order 是否消耗 AP |
| S6 行动 | 执行时间和结果是否与 AP 重叠 |
| S8 UI | 当前 AP、成本、免费动作和不足提示 |
| S10 LLM | AP 是否能控制模型调用频率 |

S5 只保留 `cost_policy` 接口，不自行定义成本。

## 五、讨论阶段

## Phase AP.0：现实现状审计

- 列出所有消耗 AP 的代码路径。
- 列出所有应消耗但未消耗的动作。
- 找出重复收费和免费漏洞。
- 收集玩家在不同界面遇到 AP 的体验。

## Phase AP.1：目的与模型选择

- 明确 AP 要制造什么决策。
- 对比候选模型。
- 决定 AP 是独立资源、时间预算还是 UI 约束。
- 决定 AP 是否继续以当前形式存在。

## Phase AP.2：成本草案

- 定义每个动作是否消耗。
- 定义成本值。
- 定义重置和超支规则。
- 定义免费动作。
- 定义紧急情况。
- 定义通信、研究和指挥成本关系。

## Phase AP.3：原型与试玩

- 用珊瑚海五月七日场景测试。
- 记录玩家是否因 AP 放弃重要交流。
- 记录是否存在无脑最优 AP 用法。
- 记录 AP 是否放大或削弱核心参谋体验。
- 必要时回到模型选择。

## Phase AP.4：规格与实施

- 输出 AP 数据模型。
- 输出成本表。
- 输出 API 与 UI 变更。
- 增加测试和遥测。
- 迁移现有 AP 调用。
- 删除重复收费路径。

---

## 六、验收标准

1. AP 的存在理由可以用一句话解释。
2. 每个消耗 AP 的动作都有明确理由。
3. 阅读和必要信息获取不能被不必要地收费。
4. AP、时间、通信和参谋负载不重复惩罚同一行为。
5. 不会因 AP 导致紧急决策无法处理。
6. 不能通过重复操作逃避成本或刷新结果。
7. UI 明确显示成本和余额。
8. 珊瑚海试玩证明 AP 增加有意义的选择。
9. 若试玩证明 AP 无价值，可以决定删除或替换它。
10. S5 和后续系统使用统一 cost_policy。

---

## 七、实施前置

在 AP 专项完成前：

- S5 不定义具体 AP 成本。
- S4 不把主动提醒处理绑定特定 AP。
- S8 只显示当前余额和已有成本。
- 新功能不得自行添加 AP 扣减。
- 所有新动作预留 `cost_policy` 字段。

---

## 八、下一步

完成 S4 核心参谋沟通讨论后：

1. 开始 Phase AP.0，审计现有 AP 代码路径。
2. 讨论 AP 的真正目的。
3. 比较候选模型。
4. 用珊瑚海场景试玩。
5. 通过后再进入 S5 正式实施。
