# 玩法系统长远路线图（gameplay-system-roadmap）

> 状态：**现行长期计划**
> 创建日期：2026-09-14
> 适用范围：UI 复现工程完成后的“玩法门”
> 组织方式：一级 = 系统，二级 = 模块
> 默认产品形态：单场战役、60–120 分钟、强重玩、带完整战后归因

---

## 一、总目标

把当前“有性格设定的问答助手”推进为一套真实参谋班子玩法：

> 玩家感知不完整事实 → 向参谋获取判断 → 下决心与授权 → 承受延迟后果 → 在战后明确归因胜负。

海战、海图和舰队模拟负责提供后果；LLM 参谋班子负责提供信息解释、人物冲突和决策戏剧。

### 不可破坏的原则

1. `GameState` 是唯一事实源。LLM 只能解释、判断和提议，不能裁定现实。
2. 所有关键回答区分【事实 / 情报来源 / 参谋判断 / 行动建议】。
3. 参谋可以错，但错误必须能追溯到能力、立场、证据或性格，不能只是模型噪声。
4. UI 必须让信息性质可见，不能依赖玩家猜测语气。
5. 胜负必须能回溯到具体决策、建议、证据和执行结果。
6. 任何系统攻坚都必须交付一条最小端到端玩法链，不能只实现孤立模块。

## 四、长期攻坚顺序

每阶段只设一个主攻系统；上下游只实现完成验收所必需的薄切片。

### 阶段 0：产品契约

- 确定一局游戏时长、胜负、玩家权限和重玩目标。
- 明确参谋是否允许比玩家更正确。
- 输出玩法契约与全局验收标准。

### 阶段 1：S2 感知与情报（已完成）

- 主攻：M2.1–M2.8，详见 `docs/plans/s2-intelligence-system-plan.md`。
- 验收：SBD 发现目标 → 电文送达 → 情报参谋研判 → 简报呈报 → 指挥官批准 → 正式标图 → 新证据修订，全链路成立。
- 实施收口：`docs/reports/s2-intel/VERIFY.md`，474 tests passed。

### 阶段 2：S3 参谋认知与判断（当前）

- 主攻：M3.1–M3.9，详见 `docs/plans/s3-staff-cognition-system-plan.md`。
- 薄切片：S2 证据、S5 授权接口、S7 复盘、S8 判断 UI、S10 行为评估。
- 首批场景：珊瑚海 1942-05-07 米西马方向错误接触与攻击决心。
- 验收：候选判断 → evidence_fit → 单次判断检定 → 人物化建议 → 新证据修订 → 认知错误和事实错误分离复盘。

### 阶段 3：S4 参谋班子与关系

- 主攻：M4.1、M4.2、M4.3、M4.4、M4.8。
- 验收：同一事件产生不同态度，立场变化有明确原因，参谋可以主动汇报。

### 阶段 4：S5 指挥、授权与执行

- 主攻：M5.1–M5.5、M5.8。
- 验收：命令、解释、授权、拒绝与执行都可审计，LLM 不越权改状态。

### 阶段 5：S6 行动、战斗与后果

- 主攻：M6.1–M6.7、M6.9。
- 验收：决策产生延迟但有意义的战果，敌方会主动行动，乌龟玩法有压力。

### 阶段 6：S7 叙事、胜负与复盘

- 主攻：M7.1、M7.3–M7.7。
- 验收：玩家能解释自己赢在哪里、输在谁身上，并能重玩验证另一种选择。

### 阶段 7：S1 世界深水区

- 主攻：M1.1、M1.7、M1.8，再补 M1.5、M1.6。
- 验收：存档、回放、天气、补给和确定性模拟成立。

### 阶段 8：S9 内容规模化

- 主攻：M9.1–M9.7。
- 验收：不修改核心代码即可生产、校验和发布新战区。

### 全程并行

- S8 交互与表现：执行 `docs/plans/s8-ui-ux-system-plan.md`；每阶段必须交付最低可用 UI。
- S10 LLM 平台与质量：每阶段都必须增加行为评估和回归场景。

## 五、系统完成门

任何一级系统只有同时满足以下条件才算完成：

1. 模块边界、数据模型、输入输出和失败模式已写入规格。
2. 规则逻辑有确定性 pytest 覆盖。
3. LLM 行为有固定场景评估，不要求固定文本，但要求行为边界正确。
4. UI 能让玩家看见该系统产生的新信息。
5. 至少完成一次真实试玩，并产生新的可归因决策。
6. 结果可以回溯到具体证据、判断、命令和行动。
7. 文档、测试、截图或复现记录与实现同步更新。
