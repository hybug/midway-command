# Midway Command：作战室 UI 设计与实现方案

日期：2026-11-19\
状态：美术方向已改以《Task Force Admiral》为主参考。下方固定桌面方案保留为上一轮原型记录。\
适用范围：珊瑚海单场景 MVP，保留后续中途岛战区的复用能力。\
技术基线：FastAPI + 原生 HTML/CSS/JS + Canvas，不引入前端框架或 3D 引擎。

## 当前美术方向

《Task Force Admiral – Vol. 1: American Carrier Battles》（TFA）为本项目的主要视觉参考。第一轮以 Demo 手册第 7 页的 **Flag Plot** 为指挥室构图参考，以第 5 页和第 28 页的 **Strategic Map** 为海图工作视图参考。参见 [TFA Demo 手册](../reference/TFA-Demo-Manual.pdf)。

| 参考视图 | 画面里值得研究的部分 | Midway Command 的设计 |
|---|---|---|
| Flag Plot | 带纵深的旗舰指挥站。舱壁、仪表和照明共同交代空间，可从室内进入具体工作站。 | 用原创舱室构图做常驻入口。视线沿桌沿进入海图，舱壁上的收报位置和桌侧工作区分别承接来电与参谋呈报。 |
| Strategic Map | 进入工作站后，二维海图占据视野。图记和局部工具服务于当前操作。 | 点海图进入清爽的全尺寸工作视图。沿用珊瑚海地理数据、可见图记和现有渲染；图面标注、选中态、开合过渡使用代码。 |

首轮验证这两个镜头之间的关系。玩家进入指挥室后能一眼找到海图，打开海图后能清楚查询报告标记和来源，返回时能认出原来的工作位置。舱室美术采用原创画面和独立器材素材，画面优先体现舰上工作环境的尺度、纵深和局部照明。界面采用自有布局、影像和图记。

两张概念图对应同一次操作。玩家从舱门望见被台灯照亮的海图桌，点桌进入海图，收到来报时右侧夹入电报。图中的英文标签和地图轮廓用于构图评审。游戏使用中文操作文案、项目里的珊瑚海地理数据和当局报告。[旗舰指挥室概念图](../assets/command-room/concept-flagship-command-post.png) · [珊瑚海海图概念图](../assets/command-room/concept-coral-sea-chart.png)

双母版的切图坐标、局部补图工单、代码接入与视觉验收见 [珊瑚海指挥室与海图实施方案](../plans/coral-sea-visual-implementation.md)。

下文的固定顶视桌面、暖黄纸张主导的构图与对应素材批次归入上一轮预览。数据权限、军令生命周期和可读性标准继续适用。

## 1. 上一轮设计结论与交付边界

下一版采用**固定视角的 2.5D 舰上作战桌**：昏暗舱室包围受灯光照亮的海图，收报盘、参谋夹、军令簿和航海日志在桌边各有位置。玩家通过阅读电报、请求判断、批准标图、签发军令和等待回报推进战局。

“2.5D”在这里指平面素材、层级、光影和短动画组合出的空间感，不做可自由游走的舱室。正文和表单保持接近正视，地图坐标准确；透视主要作用于环境和装饰。这样既能形成作战室氛围，也能在现有技术栈内完成 MVP。

本轮最重要的产品变化是：**从选择功能页，转为处理作战物件；从查看全局状态，转为接收当时能够获得的报告。**

### 1.1 完整体验目标

玩家用 20–30 分钟经历以下闭环，实际时长由试玩验证：

> 打开任务夹 → 阅读任务 → 查看海图 → 收到接触报告 → 请参谋判断 → 拟令并签发 → 推进时间 → 收到新证据或行动回报 → 调整决定 → 战局结束 → 对照当时情报复盘 → 重开。

完整方案覆盖所有环节；MVP 先实现其中必要的视图和素材，不要求一次完成所有装饰。

### 1.2 本文件与现有文档的关系

- 游戏规则仍以 [GAME_SPEC.md](GAME_SPEC.md) 及对应系统规格为准。
- 海图坐标和图层仍以 [CHART_SYSTEM.md](CHART_SYSTEM.md) 为准。
- 保留 [S8_INTERFACE.md](S8_INTERFACE.md) 的信息权限、模块职责与通知等级；本方案提议替换其外观、导航和固定顶栏布局。实现时同步修订 S8，避免两套视觉规格同时生效。
- 延续 [ART_DIRECTION.md](ART_DIRECTION.md) 的纸张、墨迹、暖光方向，但停止用整张带文字的 AI 界面图作为运行时 UI。
- 与 [珊瑚海 MVP 计划](../plans/coral-sea-mvp-plan.md) 并行。该计划原先冻结“美术重做”，本方案建议将其调整为“允许支撑本场景的有限作战桌重制”，仍冻结新战区、完整舱室和大型角色动画；在实施启动时同步修改范围。
- 当前 `command-room.css` 等未提交改动属于可用性试作，可以保留有效交互和无障碍处理，不作为最终美术风格基线。

## 2. 当前界面的具体问题

以下判断来自现有页面结构、实现与项目参考图；尚未进行新一轮玩家测试。

| 现象 | 玩家感受到的问题 | 设计处理 |
|---|---|---|
| 横向常驻工作台导航、统一页签 | 像在操作应用程序，各功能缺少空间归属 | 将入口放到固定桌面物件上，保留模块内路由 |
| 同样的矩形、标题栏、卡片组织全部内容 | 电报、人物、命令成为同一种“数据” | 电报用薄纸，参谋用名册与呈报夹，军令用带复写联的签发簿 |
| 满屏均匀的黄色纹理 | 缺少环境、桌面、纸面之间的材质和明暗层次 | 暗舱室 → 木桌 → 主海图 → 新收到的纸张，形成明确视觉前后 |
| 进入工作台后出现大块空白或密集分栏 | 像业务后台，阅读路径弱 | 每个工作站围绕一个主要物件和一个主要动作展开 |
| 状态、提示、按钮长期争夺注意 | 军情变化缺少节奏，紧张感被平均分配 | 常态安静；新情报改变收报盘；紧急报告才主动提示 |
| 技术术语暴露在文案中 | 玩家看到系统实现而非指挥行动 | “EXACT/INTENT/管线/S5”留在开发层，产品使用“指定航向/任务意图/待回报” |
| AI 参考图很丰富，真实界面复刻却易失真 | 完整图无法适应真实数据、长文本和窗口尺寸 | 用参考图确定构图，用独立素材和代码实现运行界面 |

仅增加划痕、旧纸和黄褐色滤镜不足以解决这些问题。必须同时改变布局、物件语言、信息到达方式与交互动作。

## 3. 美术方向：在值更中的作战桌

### 3.1 视觉叙事

场景是正在使用的舰上指挥空间：纸面有少量折痕、铅笔迹和工作磨损，工具有使用感，但不是废弃多年的古董陈列。采用可读的战时器物语言，具体舰型的舱室形制不在未经核实的情况下声称史实复原。

项目主参考图 `docs/assets/Gemini_Generated_Image_u1fak0u1fak0u1fa.png` 用于提取四项关系：

1. 海图是最大的受光平面。
2. 木桌和舱内暗部只在边缘交代空间。
3. 电报、刻度尺、罗盘等以不同材质提供尺度。
4. 敌情通过墨迹、标图与报告显现，画面本身不全知。

不逐像素复刻参考图：地理、文字、兵力和报告必须由当前场景数据生成。

### 3.2 材质、光照和构图规则

| 维度 | 制作规则 |
|---|---|
| 主光 | 左上约 35° 的暖白工作灯；素材亮边与阴影方向统一 |
| 环境光 | 暗绿灰舱内反光，饱和度低于纸面；正文区不叠暖色滤镜 |
| 纸张 | 海图浅米白、来电稍薄稍灰、军令较规整、日志较厚；通过色温和边缘区分 |
| 金属 | 深色拉丝金属、小范围高光；不做大面积镜面金色 |
| 木材 | 深褐低对比，木纹不与地图经纬线竞争 |
| 磨损 | 集中于纸边、折线、器具握持处；文字安全区干净 |
| 倾斜 | 主要正文 0°；次要纸张可 ±1.5°；装饰可更大，点击区域仍对齐可见物件 |
| 阴影 | 接触阴影最深；离桌物件有软投影；不同时烘焙与 CSS 重复加同一层阴影 |
| 装饰密度 | 主图有效区域不放装饰；每个工作角最多 1–2 个有叙事意义的道具 |
| 空间稳定 | 收报盘、军令簿、时钟的位置稳定；状态变化不随机搬动物件 |

### 3.3 建议色板与字体

以下为待视觉样张验证的设计 token，最终需用实际纹理合成后的颜色检查对比度：

| Token | 建议值 | 用途 |
|---|---|---|
| `--room-void` | `#151C1B` | 舱室暗部 |
| `--desk-wood` | `#332A21` | 木桌基色 |
| `--chart-paper` | `#E6DEC6` | 主海图 |
| `--document-paper` | `#F1E8D2` | 阅读纸面 |
| `--ink-primary` | `#292B27` | 正文、关键数据 |
| `--ink-secondary` | `#535348` | 来源、时间、辅助说明 |
| `--ink-friendly` | `#304D58` | 我军图记 |
| `--ink-contact` | `#853C32` | 敌情报告、危险提示 |
| `--pencil-note` | `#625E51` | 注记、草案 |
| `--focus-ring` | `#EBC77F` | 暗背景上的焦点；纸面使用深色内圈 |

- 中文正文优先可读的系统宋体/衬线字体，如 `Songti SC`、`Noto Serif CJK SC`，降级到系统中文字体。若分发字体，先核实授权并做子集。
- 命令字段、来源编号、经纬度用清晰的等宽西文字体与正常中文回退；避免全界面打字机字体。
- `Special Elite` 等旧式西文字体限于短英文题头；`Caveat` 等手写字体只用于少量装饰英文，不能承担中文军情正文。
- 正文建议 16px、行高 1.6；紧凑辅助信息不低于 13px；正文标题 20–26px。地图标签建议 12–14px，并支持选择后放大阅读。
- 中文主标签、英文副标签。历史原件风格的表头可保留短英文，但不让玩家依赖英文理解操作。

## 4. 空间布局与导航

### 4.1 基准构图：1440×900

下图是布局约束，不是最终美术稿。主海图在默认态占约 65–72% 的可用桌面面积；角落道具不得遮挡航迹和目标。

```text
┌────────────────────────── 昏暗舱室 / 桌沿 ─────────────────────────┐
│ 战区小铭牌                    舰上时钟 / 日期        值更记录       │
│ ┌─────────────────────────────────────────┐  ┌─────────────────┐ │
│ │                                         │  │ 收报盘          │ │
│ │               主 海 图                  │  │ 新来电 / 待处理 │ │
│ │       真实投影、已知接触、航迹与标图       │  │ 最上方一张摘要  │ │
│ │                                         │  ├─────────────────┤ │
│ │      点选对象 → 就近出现简短图签          │  │ 参谋呈报夹      │ │
│ │                                         │  │ 最近判断 / 请见 │ │
│ └─────────────────────────────────────────┘  └─────────────────┘ │
│ 图例 / 定位     情报夹 · 参谋名册 · 航海日志       军令簿  [等待]  │
└──────────────────────────────────────────────────────────────────┘
```

建议 CSS 布局区间：外缘 24–40px，右侧工作角 280–320px，地图与工作角间隔 20–28px，下缘工具区约 72px。顶部时钟依附桌面环境，不再使用贯穿全屏的应用顶栏。

空间入口均有清楚文字：`海图`、`收报`、`情报夹`、`参谋名册`、`航海日志`、`签发军令`。物件隐喻不能成为谜题，首次悬停、键盘焦点和首局引导都应显示用途。

### 4.2 逻辑模块与物件对应

| 现有模块 | 新视觉入口 | 打开后主要物件 | 返回方式 |
|---|---|---|---|
| CHART | 海图本身 | 主图与对象图签 | 默认态 |
| COMMS | 右上收报盘 | 展开的电报 + 来电目录 | 放回收报盘 / Esc |
| INTEL | 下缘情报夹 | 情势摘要、证据附件、待批标图 | 合上情报夹 / Esc |
| STAFF | 下缘名册、右侧呈报夹 | 人员索引 + 当前人员呈报纸 | 返回海图 / Esc |
| LOG | 下缘航海日志 | 按时间排列的日志页 | 合上日志 / Esc |
| ISSUE ORDER | 右下军令簿 | 一份军令正文和签发联 | 收起草稿 / Esc |

这些入口在代码内仍可以使用原有模块标识，不必重写后端架构。`ISSUE ORDER` 仍为唯一正式签发入口；从参谋建议或地图进入时，只带入草稿上下文。

### 4.3 聚焦阅读模式

- 打开电报等物件时，用 180–280ms 的平移与缩放形成“拿到面前”的连续感，正文最终保持正向。
- 聚焦物件占桌面约 70–85%；保留一圈环境和原入口，维持方向感。窄屏可切换为全屏纸面阅读。
- 长文本在纸面内容区滚动，题头、返回和必要动作保持可见；不让全文缩小到一张图片内。
- 一次只打开一个主物件。证据附件可做侧页，避免多层窗口叠加。
- 从电报跳到标图，再返回时恢复原电报与滚动位置。关闭后焦点回到触发物件。
- 计时行为沿用游戏规则：打开或关闭界面不主动推进时间；不得把环境动画暗示成自动流逝的游戏时间。

## 5. 全流程逐场景设计

### 5.1 标题、场景选择与任务简报

**画面**：同一张工作桌的远景，上面有场景任务夹。主标题像档案封签，场景以夹内任务封面呈现；不做产品介绍式大标语和营销卡片。

**信息**：场景名、玩家身份、日期与地点、预计体验时长、有限目标、史实启发/规则简化说明。MVP 优先展示珊瑚海，其他已有场景保持次要入口，不伪装成已完成的新内容。

**交互**：选择任务夹 → 阅读简报 → `接任指挥`。简报解释“情报可能错误”“建议需要签发”“等待会推进战局”，以三段简短说明配对应物件示意。

**实现**：背景用可复用房间图层；任务夹用切图边缘 + CSS 表面；全部文字和按钮用 DOM。切换动画只是过渡，不在背景图中写死场景名。

**状态**：读取场景、加载失败、创建游戏中、防重复启动。失败保留选择和简报，可明确重试。

### 5.2 默认海图与态势查看

**画面**：大幅平展海图是视觉主角。地理和网格墨色较轻，舰队标识与最新有效标图较重。必要的铅笔、尺只位于边缘。

**信息层级**：

1. 我军位置、当前航向、已批准且已获知的接触标图。
2. 搜索区、任务航线、已知历史航迹；用线型区分意图、执行任务和历史。
3. 经纬网、岛屿、地名、比例和图例。

**交互**：

- 点击舰队或接触出现简短图签，提供来源时间、已知性质和相关操作。
- 接触图签明确写“报告称……”“距报告时间……”，不把估计位置描绘成正在追踪的精确目标。
- 待批标图只在“审核标图”模式中以铅笔虚线显示，默认图不出现。
- 鼠标滚轮缩放、拖动平移、`定位我军/恢复全图`作为拟增加能力，需单独验证坐标转换与标签命中；第一版可先保留固定视野和定位按钮。
- Canvas 外提供“海图对象列表”，键盘玩家可选中对象并打开同一图签。

**实现**：保留 `chartRenderer.js` 与 `mapRenderer.js` 的数据驱动层；纸纹为背景素材；地理、标记、路线、选中态由代码绘制。禁止将 AI 海图上的岛屿、舰船或网格当成真实坐标。

**空态**：没有敌情时写“尚无可标绘的接触报告”，不得写“海域安全”。无正在进行的行动时，不用装饰性飞机在图上飞行。

### 5.3 收报与阅读来电

**画面**：右上收报盘露出最新一张电文的题头，纸叠厚度表现有待阅内容，但数量同时以文字提供。点击后展开一张来电，旁边是窄目录。

**正文顺序**：优先级 → 收报时间/原始报告时间 → 发报人及转呈链 → 原文 → 译读或摘要 → 相关证据 → 可采取动作。

**动作**：`阅毕`、`请参谋判断`、`查看关联标图`。前两者不能擅自改变敌情标图；只有明确批准的标图提案进入默认海图。

**到达节奏**：普通来电只改变纸叠与未读数字；FLASH 用一次短提示和可选报务音，提供打开按钮，不抢走输入焦点。玩家正在编辑命令时保留草稿。

**实现**：纸形边缘可以切图；折线、打孔、横线用 SVG/CSS；文字、来源链、优先级必须实时排版。长电文不拉伸整张纸图，而是中段平铺或九宫格扩展。

**状态**：未读、已读、勘误、关联已失效。勘误保留原报告并附修订，不直接覆盖玩家之前看到的内容。

### 5.4 情报夹、证据与标图审核

**画面**：打开的档案夹，主纸是“当前情势判断”，右侧少量露出的附件索引对应证据与待批标图，不做大面积 KPI 磁贴。

**主纸内容**：已知内容、存在争议的内容、仍未知的内容、建议下一步。摘要只能来自玩家可见的情报和判断。

**证据表现**：原文摘录带来源编号和时间；相互矛盾的报告并排放到两张附件纸上，标出冲突具体在哪里。使用“报告/判断/推测”文字标识，颜色只作辅助。

**标图审核**：左侧或上半部显示聚焦海图，右侧显示依据与候选解释；提供 `批准标图`、`请修订`、`暂缓`、`驳回`。批准前后的线型与状态明确变化。

**限制**：置信措辞使用后端提供的等级；不在前端根据样式生成百分比，不绘制未经授权的“真实敌军范围”。

### 5.5 参谋名册、交流与分歧

**画面**：左侧窄名册，主区为一位参谋的呈报纸，右上可有小肖像/身份照。首次进入默认显示当前相关人员，不让空白聊天框占满屏幕。

**身份**：姓名、军衔、岗位、所在舰、是否可直接联络。场景名单来自后端；不能为了排版填入别的战区人物。

**呈报结构**：`我的判断` → `依据` → `建议` → `什么新消息会改变此判断`。自然语言体现人物，结构帮助阅读。

**交流结构**：历史对话像按时间排列的问答记录，而非即时通讯气泡；底部有稳定的输入区和真实字段标签。快捷问题填入输入框或明确发起请求，不能暗扣资源。

**分歧**：展示两份已经送达的判断及其证据差异。不给玩家看“能力 83/信任 62/真实性 91%”等内部数值。

**能力差异**：有些人员支持聊天，有些支持正式判断或转呈；依 `contact_permission` 和实际能力显示动作，不承诺人人都可聊天。

**等待/失败**：显示“请求已送出/正在形成判断”等与真实请求一致的反馈。模型超时保留问题，可重试，失败不伪造电报或判断。

**美术取舍**：P0 使用文字身份牌和通用照片框；人物肖像为 P1。MVP 不做全屏立绘、口型动画和拟真的“真人视频”。

### 5.6 军令簿：拟令、核对、签发、回报

**画面**：一份带表格线的军令，旁边露出复写联。草稿铅笔注记、签发墨迹、收到回执的印章具有不同语义。

**草稿字段**：受令单位、命令类型、任务意图、航向或区域、兵力与时间约束、依据。按 `/orders/catalog` 返回的可用能力展示字段。

**签发前核对**：在同一纸面显示人类可读的命令摘要、资源及限制的后端校验结果，然后 `签发军令`。自然语言拟令产生的参数须可检查和修改。

**地图上下文**：从海图选点或参谋建议进入时，先放入未签发草稿；坐标和建议依据显式可见，不能点击建议就执行。

**显示状态**：草稿 → 已签发 → 传达情况 → 已报告的行动进展 → 回报。以公开视图中的真实状态映射，不能强迫所有命令经过目前后端不支持的阶段。

**印章语义**：

- `已签发`：仅在签发请求成功后出现。
- `已送达`：仅在有对应公开回执时出现。
- `已回报`：仅在行动报告送达后出现。
- 禁止根据客户端计时自动盖“完成”章；请求成功也不等于攻击成功。

**当前边界**：统一军令目录目前只有改变航向和放飞侦察。攻击表单及生命周期列入 MVP 后端批次；接口未就绪前不放可点击的假功能，也不另建绕过统一军令的执行入口。

**状态**：校验失败定位到字段；提交时禁止重复签发；网络结果不确定时先查询命令记录再允许重试，避免重复行动。取消只在后端允许时出现。

### 5.7 等待、时间与行动过程

**画面**：舰上时钟保持可见；桌边有清楚标记的 `等待 5 分钟` 等按钮，具体步长由规则允许值决定。文字必须告诉玩家推进多少游戏时间。

**反馈**：提交后短暂锁定重复操作；成功后时钟更新、海图更新、收报盘接收已送达的报告。可以用短声和轻微纸张移动串联结果。

**诚实表达**：只显示已公开的行动状态；不能显示隐藏飞机与敌军的实时精确动向、秘密阶段或未送达战果。无新回报时写“尚未收到新回报”。

**资源/AP**：保留当前规则的真实成本。若游戏仍使用 AP，在值更记录或动作核对区写“本轮可用行动/本次消耗”，不用无语义的游戏货币图标。本设计不修改交流、阅读或等待的 AP 规则。

**节奏**：不强制玩家观看长动画。完成后的关键报告可直接打开；不让动画等待成为新的操作成本。

### 5.8 航海日志与战后复盘

**战中**：日志按时间展示已经获得的情报、判断、命令与回报；可按事件定位原件。这里是“当时知道了什么”的记录。

**结束过渡**：以“本阶段作战结束”的简短通知进入结案卷宗，说明结束原因、目标达成情况和可确认的损失；结果未定时保留不确定措辞。

**战后**：提供三个阅读层次：

1. 一页结果摘要：任务目标、关键决定、主要后果。
2. 决策时间线：当时证据 → 参谋判断 → 玩家命令 → 后续报告。
3. 可选对照：当时认知与场景真值的差异，明确标注“战后揭示”，并与战中记录隔离。

**操作**：`重新执行本场景`、`返回任务选择`。重开提示会清空本局记录，不设计当前尚不存在的存档读取功能。

**后端依赖**：战后真值必须由后端阶段权限控制。仅在界面隐藏按钮不能修复目前复盘接口可在战中访问的问题。

### 5.9 设置、帮助与异常

- 桌沿一个清楚标记的 `设置/帮助` 入口；提供音量、静音、减少动态、文字大小、图例和操作说明。
- 环境音默认静音，玩家主动启用后再播放；记住本机偏好。无音频也能完整接收所有消息。
- 不把网络失败解释为剧情中的通信受阻；使用独立的清楚提示：“连接失败，本次操作尚未确认”，提供恢复路径。
- 文字放大后允许纸面滚动、目录收起；不能通过裁掉正文维持美术构图。

## 6. 代码、切图与 AI 的明确分工

这里的“切图”指按布局需要制作并交付可复用边框、物件、透明图层，包括从现有素材或 AI 源图中提取、手工修边；不是截一张完整界面当按钮。

| 对象 | 最终实现方式 | AI 的作用 | 必须由代码掌握的部分 |
|---|---|---|---|
| 舱室远景/桌缘 | 低细节背景图 + CSS 色调/暗角 | 可生成无文字、留白构图底图 | 响应式裁切、亮度、加载回退 |
| 木桌表面 | 平铺纹理 + CSS | 可补充材质样本 | 覆盖区域、纹理尺度、明暗 |
| 海图纸张 | 低对比纸纹 + CSS/SVG 边缘 | 只生成材质 | 地理、经纬线、文字、位置、缩放 |
| 岛屿/网格/航迹/搜索区 | Canvas/SVG | 不参与数据图形生成 | 全部几何与标注 |
| 舰队/敌情图记 | 清晰 SVG 或经筛选的 PNG | 可做装饰筹码的底材 | 标识内容、方向、状态、命中与图例 |
| 电报/军令/日志 | DOM + CSS 排版 + 可延展切图边 | 生成无字纸材、封皮质感 | 正文、字段、时间、状态、来源 |
| 收报盘/文件夹/夹扣 | 独立透明物件图 + DOM 热区 | 适合生成统一光照源图 | 数量、选中态、标签、交互 |
| 印章 | SVG 轮廓 + 实时文字/可控印痕 | 可提供纹理参考 | 印章内容、状态语义、出现条件 |
| 时钟 | SVG 表盘 + DOM/SVG 指针与日期 | 可选金属外壳底图 | 游戏时间、时区标识、读数 |
| 肖像 | 独立照片素材，P1 | 经史实身份核对后生成演绎性形象 | 姓名/军衔/权限，不能画在照片里 |
| 光照/阴影 | CSS 渐变、蒙版、阴影 | 提供样张光照参考 | 层级、强度、对文字的保护 |
| 通知/焦点/表单/错误 | DOM + CSS | 无需生图 | 全部状态、无障碍、操作反馈 |
| 动效 | CSS/Web Animations API | 无需逐帧生图 | 动作时机、取消、减少动态 |
| 声音 | 有授权的音效或自行录制，P1 | 不在本次图像生产范围 | 触发、音量、静音、重复限制 |

**最值得 AI 生图的部分**是环境、材质和少量器物；**最值得人工精修的部分**是纸边、透明轮廓和道具的一致性；**最值得代码实现的部分**是所有决定游戏含义的信息。

## 7. 素材清单与交付规格

### 7.1 交付约定

- 设计源文件与评选稿放在 `docs/assets/command-room/`；运行文件放在 `static/assets/command-room/`。这两个目录为计划新增。

### 7.4 切图与九宫格标准

1. 纸张母版分四角、边、中心，建议固定边缘 24px；CSS `border-image` 或等价切片实现。实际边宽以原图清晰度调整，不能默认拉伸整图。
2. 独立道具的透明画布保留至少 8% 外围空间，防止投影被裁。输出同时检查真实轮廓和投影轮廓。
3. 默认优先“无投影主体 + 代码阴影”；复杂镂空物件可提供单独投影图层，禁止主体自带重影再叠同向重影。
4. alpha 边缘在浅纸、深木、绿色测试底上检查；没有绿边、白边、黑边、孤立像素和误切文字残片。
5. 收报盘的前缘、纸张、底盘分层，否则纸张无法看起来放进盘内。军令簿的装订边与正文分离。
6. 所有图像必须有 100%、50%、实际显示尺寸三档预览；不以源图放大后“细节很多”作为可用标准。
7. 现有 47 张提取素材逐项筛选，不把“已抠图”等同于可交付。优先独立透明素材，不再依赖巨型绿幕混排表批量取图。

## 8. AI 生图制作简报

本节提供制作模板，本轮不实际生成图片。首张整场景图用于定调和画面评审，正式运行仍拆成第 7 节的独立图层。

### 8.1 统一风格锚点

所有提示词附带以下约束，并尽可能传入同一张通过评审的风格参考图。不同工具的 seed 可重复性不同，不依赖 seed 单独保证一致性。

> 1942 Pacific naval command-table art direction, restrained cinematic realism, functional wartime workspace, warm task light from upper left, subdued green-gray ambient shadows, dark low-contrast wood, lightly used cream paper, physically consistent scale, clean readable center, no modern electronics, no neon, no fantasy machinery, no written text, no letters, no numbers, no logo, no watermark.

### 8.2 整体构图样张

> Fixed near-overhead view of a compact naval plotting table in a dim ship interior. A large blank cream chart sheet occupies the left and center; a simple incoming-message tray sits at the upper right, a closed order pad at the lower right, a narrow logbook at the lower edge. Keep the paper entirely blank and the central working area unobstructed. Show only a modest rim of dark wood and a suggestion of the surrounding compartment. Unified warm light from upper left. Landscape composition, 16:10. [统一风格锚点]

评审重点：第一眼是否先看见海图；桌面和纸面是否有空间关系；右侧物件是否有足够空间容纳真实文字。此图不直接作为整屏产品。

### 8.3 环境底图 A01

> Empty dark wooden naval worktable with a subtle border of dim green-gray ship interior, fixed near-overhead view. No papers, no tools, no clocks, no instruments on the central surface. Low-detail center reserved for application layers. Soft upper-left task lighting, subdued outer edges. [统一风格锚点]

后处理：保证中心无烘焙物件和强阴影；实际亮度可由代码调整。不额外生成一个已带巨大海图的底图再叠第二张海图。

### 8.4 纸材 A03/A04

> Flat scan of lightly aged cream drafting paper, fine natural fibers, extremely subtle wear, even neutral illumination, no dramatic stains, no writing, no printed map, no fold shadow, seamless material sample. [材质部分沿用风格锚点，移除场景投影要求]

可平铺是交付要求，不假设 AI 输出天然无缝；必须后处理检查。

### 8.5 收报盘等单物件 A06

> One empty shallow dark-metal incoming-message tray, isolated object, fixed near-overhead view matching the approved command-table reference, warm light from upper left, no labels, no contents, no text. Preserve its full silhouette with generous clear padding. Separate front lip visually from the interior. [统一风格锚点]

工具支持透明背景时直接要求透明。若不支持，使用易抠的纯色背景并人工修边；不默认使用绿幕，避免金属反射带入绿边。

### 8.6 人物肖像 A14

先准备经过核对的身份说明、服装参考及合法参考图，再写角色专用提示词；本方案不臆造每个人的军衔、制服徽记和长相。统一灰阶、相同裁切与光照，不把姓名、军衔画进照片。没有可靠人物依据时先保留文字身份牌。

### 8.7 每轮评审与返工

- 整体构图先少量比较，选定一种光照与材质后再批量做物件。
- 物件评审按“比例—光向—轮廓—材质—可切性—实际尺寸”顺序，避免只选好看的孤立图。
- 单个器物无法与场景一致时重做该器物，不能为迁就它改变整套光照。
- 每轮保存联系表和淘汰原因。大背景通过不等于纸边、人物和战术图记自动通过。

## 9. 工程实现方案

### 9.1 画面分层

```text
环境图与桌面纹理（不接收指针）
  → 桌面装饰与接触阴影（不接收指针）
  → 海图纸面 / 静态地理 Canvas
  → 动态战术 Canvas / DOM 图签 / 海图工具
  → 桌边物件入口与常态收报摘要
  → 单个聚焦物件：电报 / 情报夹 / 名册 / 军令 / 日志
  → 关键提示与确认
  → 战后结案视图
```

采用一份明确的 CSS 层级表；暗角等环境层放在内容后方或避开正文，不沿用“所有内容上再盖一层噪声”的做法。装饰图设 `pointer-events: none`、`aria-hidden="true"`。

### 9.2 现有模块的改动边界

| 文件/模块 | 保留 | 计划调整 |
|---|---|---|
| `static/index.html` | 启动入口、语义标签、现有业务挂载点 | 删除应用式永久导航外观，增加桌面物件布局和聚焦容器 |
| `static/css/style.css` / `command-room.css` | 有效可读性和响应式经验 | 收敛成明确 token、布局、物件组件层；迁移后删掉冲突覆盖，不继续堆更高优先级规则 |

| `commandDesk.js` | 注册区块与路由机制 | 单主物件切换；显式 mount/unmount，清理旧监听/轮询，保存阅读状态 |
| `commsDesk.js` | 原文、来源与频道数据 | 来电目录 + 单电文纸面，未读/勘误样式 |

### 9.3 数据与接口对照

以下区分“路由已经存在”与“足以支撑所提设计”，不能因路由存在就认定数据安全、字段和场景均已完备。

| UI | 现有接口/来源 | 实施时待核对或补齐 |
|---|---|---|
| 任务选择/开局 | `GET /theaters`、`POST /game/new`、`GET /theater` | 简报内容、场景目标、时限与结束原因的公开字段 |
| 海图/时钟/我军 | `GET /state`、`GET /routes` | 新字段只走玩家视图；实际投影沿用战区数据 |
| 来电 | `GET /intel/inbox`、`GET /comms/channels` | 原始时间与收报时间、未读语义、转呈链 |
| 证据/情势/标图 | `/intel/sitrep`、`/intel/evidence`、`/intel/briefs`、`/intel/plots` 及对应批准/历史接口 | 审核预览与默认图分离；冲突只来自已公开证据 |
| 人员与判断 | `/staff/roster`、`/staff/channels`、`/staff/notices`、`/staff/reports`、`POST /chat`、`POST /judgment/tasks` 及结果接口 | 场景名单、不同人员能力、请求状态和失败 |
| 军令 | `/orders/catalog`、`/orders/draft`、`/orders`、`/orders/{id}/issue` 等 | 攻击统一接入；核对创建/签发返回是否含内部执行字段，前端只消费批准的公开字段 |
| 推进 | `POST /advance` | 非法时间、场景截止、结束后禁止推进，由后端修复 |
| 日志/复盘 | `/log/timeline`、`/log/after-action`、`/intel/after-action` | 战中白名单与战后真值权限；不能只靠前端分路由 |

接口适配层负责把字段转成 UI 展示模型，禁止为了“显得完整”在前端补造状态、置信度、人物或战果。开发样例只能在明确的开发入口启用，正式页面不能静默退回假数据。

### 9.4 请求、生命周期与素材加载

- 按现有请求方式渐进改造，不为美术重制引入新的实时通信基础设施。
- 公共态势统一刷新；当前聚焦模块按需加载，隐藏模块停止自身轮询。切换时中止过期请求或按请求版本丢弃响应。
- 使用游戏/场景标识隔离本局缓存；重新开始后旧请求不得写入新局 UI。
- 核心纸纹、桌面、字形和图记先加载；人物、附图和声音按需加载。
- 图片失败时用纯色纸面/简化 SVG 回退，正文、海图和签发保持可用。
- 每张图声明尺寸或比例，防止加载后物件跳动。素材版本和 HTML 缓存参数一起更新。

## 10. 动效、音效与信息节奏

| 触发 | 视觉 | 声音（启用时） | 建议时长 |
|---|---|---|---|
| 打开任务夹 | 封面小幅移开、简报进入 | 短纸声 | 240–360ms |
| 常规新来电 | 收报盘纸张轻推入，不覆盖当前任务 | 可选很轻的报务提示 | 160–240ms |
| 紧急来电 | 一次重点提示，保留打开入口 | 一次短报务音 | 200ms 左右；不持续闪烁 |
| 聚焦纸面 | 从入口移动到阅读位置 | 短纸声 | 180–280ms |
| 批准标图 | 草案线变为正式墨线 | 可选铅笔/纸声 | 120–200ms |
| 签发成功 | 印章短促落下，仅一次 | 一次落章声 | 120–180ms |
| 推进成功 | 时钟更新、已知态势重绘 | 可选短刻度声 | 不强制播放等待片段 |
| 战局结束 | 海图收暗、结案卷宗呈现 | 短转场声 | 350–500ms，可跳过 |

`prefers-reduced-motion` 下取消搬移、旋转与抖动，直接切换最终态或短淡入。不得逐字打印关键情报；玩家需要立即读完正文。声音同类高频事件做合并，连续多封来电不叠成噪声。

## 11. 响应式、可读性与无障碍

### 11.1 视口策略

| 视口 | 布局策略 |
|---|---|
| 1920×1080 / 1440×900 | 完整桌面；增加留白和海图视野，不无限放大纹理与文字 |
| 1366×768 / 1280×720 | 减少装饰边缘，右侧收紧到约 260px，正文区可滚动 |
| 1440×662 等低高度窗口 | 高度断点优先；物件入口收成桌边窄标签，纸面近全高；签发与关闭保持可达 |
| 超宽屏 | 主内容最大宽度约 1800px，外围显示舱室暗部；不把电报拉成整屏长行 |
| 平板横屏 | 海图主视图 + 可收起收报抽屉，点击与键盘均可用 |
| 小于 900px 宽 | 简化为海图与纸面切换，保留清楚文字导航；不同比缩小整个作战桌 |

MVP 验收重点为桌面与低高度窗口；手机不作为主要游戏体验，但应避免内容和关键操作被裁掉，不伪称完整手机适配已完成。

### 11.2 交互底线

- 正文对比度目标至少 4.5:1；纹理、阴影叠加后实测，不能只检查色板。
- 点击目标至少 44×44 CSS px；装饰物细小，不代表点击区域必须细小。
- 所有物件入口使用真实 `button` 或语义等价控件，提供名字、焦点和可见状态。
- 聚焦视图进入时移动焦点，必要时限制焦点在当前对话框内；Esc 返回，焦点恢复。
- 地图颜色同时配合形状、线型和文字，不用红绿区别所有状态。
- 通知使用适当的 live region；输入期间的新来电不夺焦点。
- 200% 文字放大时关键正文和签发操作可达；没有 hover 也能发现功能。

## 12. 性能与质量预算

以下是验收目标，需在目标设备实测，不是当前性能结论。

| 项目 | 目标 |
|---|---|
| 首次进入作战桌核心视觉素材 | 压缩后合计尽量不超过 3MB；人物、附图、声音不计入首屏预载 |
| 单张环境底图 | 尽量不超过 800KB；避免同时保留多张 4K 背景 |
| 单个常用透明道具 | 尽量不超过 200KB；超过时先裁掉无效透明区并评估尺寸 |
| 贴图内存 | 活跃视觉素材解码后预算约 64MB；按宽×高×4 估算后实测，文件小不等于显存小 |
| Canvas | DPR 建议上限 2，可按设备调整；不让每个隐藏工作台各持一个大 Canvas |
| 动画 | 目标设备上接近 60fps；纹理静态合成，避免全屏 `filter: blur` 与持续阴影动画 |
| 静止界面 | 无必要时不持续重绘整个桌面；动态海图按实际更新需要重绘 |
| 输入反馈 | 本地交互即时给出状态；网络/LLM 等待独立显示，不要求模型在固定毫秒内返回 |

纹理首先是材质信息，不是分辨率竞赛。阴影、少量纸边和合理的空间关系，通常比每个面板一张大图更有价值。

## 13. 制作与实施批次

### 批次 A：视觉定调与灰盒构图

**产出**

- 1440×900 默认作战桌构图。
- 1280×720 与低高度窗口构图。
- 三张关键状态稿：阅读紧急电报、参谋判断、签发军令。
- 一张包含木、纸、金属、墨迹和图记的材质/字体对照板。

**做法**：先以 CSS/简单 SVG 灰盒验证物件位置和真实文本，再用 1 张 AI 概念图统一光照；关键状态稿可以由同一套原型切换得到，不必让 AI 分别画五套界面。

**通过标准**：没有巨大常驻应用导航；海图主次清楚；玩家能找到收报、参谋和签发入口；真实长电文和军令字段放得下。此批通过后才批量生产道具。

### 批次 B：核心素材与可运行作战桌

**产出**：A01–A10 全部交付或确认复用；启动、海图、桌边入口、聚焦纸面、时间与通知接入。

**通过标准**：真实游戏数据可运行；无图时功能可回退；窗口变化不破坏位置和命中；无重复阴影、错光、抠图边。

### 批次 C：完整指挥流程

**产出**：收报 → 情报/参谋 → 标图 → 草稿/签发 → 推进 → 回报 → 日志。与后端 MVP 批次并行对接。

**通过标准**：玩家完成至少两次有依据的决定；每次操作的反馈真实；聊天、拟令和正式执行分明；战中没有真值泄漏。

### 批次 D：结束、复盘与体验增强

**产出**：结案、决策时间线、战后对照、重开；按价值加入 P1 道具、照片与短音效。

**通过标准**：一局完整结束，能解释决定如何影响结果；静音、减少动态和图片失败均可玩；重开不残留旧局消息。

### 批次 E：试玩与收口

邀请 3–5 名未参与开发者试玩。记录首次找到入口的耗时、是否看懂来源/不确定性、是否误把草稿当已执行、是否能结束并重开；先修流程阻塞，再修装饰细节。

不按“完成了多少张图”判断进度；按“玩家已能走通哪一段真实流程”判断。

## 14. 并行分工与依赖

| 工作流 | 负责范围 | 可以独立做 | 必须会合的地方 |
|---|---|---|---|
| 前端/交互 | 桌面布局、纸面组件、焦点、通知与动作反馈 | 灰盒、既有接口适配、响应式 | 公开状态、错误语义、结束与重开 |
| 美术/素材 | 光照样张、纸边、道具、图记与素材清单 | 按已定构图制作资产 | 与实际 CSS 尺寸、裁切、文字安全区核对 |
| 后端/玩法 | 时间、信息边界、攻击生命周期、结局 | 按 MVP 计划修规则和测试 | 字段可见性、命令能力、回报、战后权限 |
| 验收 | 浏览器真流程、视觉截图、玩家理解 | 基准视口、长文本、失败状态 | 完整游玩闭环与信息安全 |

先约定四个契约：场景与结束公开信息、人员能力、命令公开状态、已送达情报。接口变化用样例响应和回归测试同步；不让前端根据字段名字猜权限。

如在同一仓库并行：前端主要拥有 `static/`，后端主要拥有 `server.py`、`src/`；共享契约和 `tests/` 提前划分文件范围，避免两边同时改同一入口。素材生产不改业务 JS。

## 15. 验收方案与退出标准

### 15.1 工程验证

- 依仓库规则，为新交互先补能验证行为的回归测试，再实现。优先覆盖签发防重、草稿保留、焦点恢复、模块切换清理、重开隔离及公开状态映射。
- 静态检查保证素材存在、HTML 入口正确、装饰不拦截、缓存号一致；不把“某个 CSS token 存在”当作沉浸感已达标。
- 后端独立验证战中权限、非法推进和命令幂等相关约束。
- 执行适用测试及最终全量测试；本环境既有可用命令为 `python -m pytest tests/ -q -p no:capture`。
- 现有 UI 试作曾有缓存号守卫失败：测试期望旧版本号，页面使用新版本号。正式实施时一并更新版本契约并复跑，不能把历史通过记录当成当前全绿。

### 15.2 浏览器截图清单

至少在 1440×900、1280×720、1440×662 验证以下状态；保存到拟新增的 `docs/reports/command-room/`：

1. 任务夹与已加载简报。
2. 正常海图，包含真实我军与已批准接触。
3. 新来电与一张长电文。
4. 冲突证据与待批标图。
5. 一位参谋的真实返回判断及等待/失败状态。
6. 军令草稿、字段错误、签发成功及等待回报。
7. 战局结束、复盘及重新开始后的干净状态。
8. 文字放大、键盘焦点、减少动态，以及至少一项素材加载失败。

截图必须等内容加载完成；空白纸面、骨架屏或“正在扫描档案”不能充当完成验收。视觉评审同时看实际尺寸和交互录屏。

### 15.3 产品退出标准

- 第一眼识别为海上作战指挥桌，能区分海图、电报、军令与日志。
- 主任务入口可发现；常用路径不被装饰增加额外层级，阅读报告到请求判断或拟令有直接通路。
- 来源、时间、不确定性和命令阶段无需理解内部系统术语。
- 一局能从简报走到结果、复盘和重开；玩家能解释至少一个决定的依据与后果。
- 纸纹、光影和动效不降低阅读、命中与性能。
- 战中只有玩家可知信息；战后揭示有明确边界。

## 16. 主要风险与取舍

| 风险 | 对策 |
|---|---|
| 做出漂亮静态桌面，但真实文本放不下 | 批次 A 就使用实际最长电报、人员姓名和军令字段 |
| 为追求沉浸把入口藏得过深 | 物件始终有文字标签；新玩家测试发现性；保留键盘与简化布局 |
| 纸张过旧、噪点过重导致疲劳 | 正文安全区低纹理，磨损集中在边缘，纸面亮度优先 |
| AI 图之间光照、透视与比例不一致 | 一套风格锚点，单物件交付；以放进真实页面后的效果淘汰 |
| 海图艺术化后损坏坐标精度 | 地理与战术完全由数据绘制，素材不承担位置含义 |
| 视觉展示了后端还没有的能力 | 可用命令和人员动作来自目录/权限；设计稿标明依赖，正式版不假实现 |
| 美术占用 MVP 全部工期 | P0 只做 10 个资产族，优先复用，P1 在闭环之后 |
| 继续叠 CSS，历史规则互相覆盖 | 迁移过程中保留回退点，完成后收敛为一套正式外壳 |
| 用漂亮界面掩盖信息泄漏 | 接口权限测试独立验收；前端隐藏不是安全边界 |
